# MODX3 MCP — руководство по разработке и обслуживанию

Этот документ нужен тем, кто хочет **запустить, обслуживать или развивать MODX3 MCP**.

Он написан так, чтобы опытный разработчик быстро понял архитектуру проекта, точки расширения, ограничения и порядок проверки изменений. Человек без глубокого опыта в MODX тоже сможет понять общую схему и увидеть, что именно требует внимания, но этот документ не заменяет знания PHP, Node.js, MODX и работы с сервером.

Для обычной установки достаточно готового релиза и настройки MCP-клиента. Разработка, изменение серверной логики, настройка безопасности, обновление на рабочем сайте и разбор нестандартных ошибок уже требуют технической квалификации. Если после чтения соответствующего раздела вы не можете уверенно объяснить, что именно будет изменено и как это проверить, лучше не экспериментировать на рабочем сайте и привлечь специалиста.

Документ можно передать ИИ-ассистенту перед работой с проектом. В этом случае ИИ должен использовать его как правила проекта: сначала разобраться, что именно он собирается менять, затем объяснить последствия и только после этого вносить изменения. ИИ может сильно упростить работу, но не снимает ответственность за доступы, резервные копии, проверку изменений и выбор подходящего тестового окружения.

MODX3 MCP предназначен для **MODX Revolution 3.x**. Инструкции, написанные для старой линии MODX 2, нельзя переносить сюда автоматически: в MODX 3 изменились классы PHP, пространства имён, загрузка ядра и расположение встроенных процессоров.

> **Главный принцип проекта: ИИ должен получать не максимально широкий доступ к сайту, а правильный, ограниченный и проверяемый доступ к объектам MODX.**

## 1. Как всё работает

В системе есть две основные части.

Первая часть устанавливается **на сайт MODX**. Это PHP-компонент, который умеет работать с ресурсами, шаблонами, чанками, сниппетами, TV-полями, настройками, дополнениями и другими объектами MODX.

Вторая часть запускается **рядом с программой, в которой работает ИИ**. Это локальный сервер MCP на Node.js. Он показывает ИИ доступные инструменты и передаёт выбранную команду на сайт.

Упрощённо цепочка выглядит так:

```text
ИИ или программа с поддержкой MCP
      ⇅
локальный сервер MCP на Node.js
client/index.js
      ⇅ HTTPS + API-токен
API на сайте
assets/components/modxmcp/api.php
      ⇅
основная логика MODX3 MCP
core/components/modxmcp/model/modxmcp.class.php
      ⇅
MODX Revolution 3
```

Смысл этой схемы в том, что ИИ не обязан напрямую менять таблицы базы данных MODX или произвольные файлы. Он вызывает понятную операцию: например, «получить чанк», «найти, где используется TV», «изменить ресурс». Серверная часть уже выполняет эту операцию средствами MODX.

У компонента также есть собственные страницы в менеджере MODX: настройки и экран графа зависимостей.

## 2. Что нужно для обычного запуска

Если вы просто хотите пользоваться MODX3 MCP, изучать весь исходный код не нужно.

Порядок такой:

1. Установить готовый транспортный пакет MODX3 MCP на сайт.
2. Получить автоматически созданный API-токен.
3. Настроить программу с поддержкой MCP так, чтобы она запускала Node.js-часть MODX3 MCP.
4. Передать ей адрес API сайта и API-токен.
5. Сначала проверить работу на операциях только для чтения.
6. Разрешать изменяющие и опасные операции только по мере необходимости.

Для стабильной работы лучше использовать конкретный релиз, например `v1.0.0`, а не текущую рабочую ветку.

Пример настройки MCP-клиента:

```json
{
  "mcpServers": {
    "modx": {
      "command": "npx",
      "args": [
        "-y",
        "github:rumata-estor/modx3-mcp#v1.0.0"
      ],
      "env": {
        "MODX_MCP_SITE_URL": "https://example.com/assets/components/modxmcp/api.php",
        "MODX_MCP_TOKEN": "your-token"
      }
    }
  }
}
```

Для локальной части нужен **Node.js 18 или новее**.

После подключения лучше начать с простой безопасной задачи: показать структуру проекта, получить известный элемент или построить граф зависимостей.

## 3. Основные части проекта

Ниже — краткая карта репозитория.

### `client/index.js`

Локальный сервер MCP на Node.js.

Здесь находятся:

- описания инструментов, которые видит ИИ;
- отправка запросов на сайт;
- разделение операций на чтение и изменение;
- автоматические резервные копии перед частью изменений;
- блокировка одновременных изменений одного проекта;
- внешний обработчик журнала изменений;
- дополнительные ограничения для опасных операций.

### `assets/components/modxmcp/api.php`

API на сайте.

Он:

- требует HTTPS по умолчанию;
- проверяет API-токен;
- ограничивает размер запроса;
- принимает команду от локального MCP-сервера;
- передаёт её основной серверной логике.

### `core/components/modxmcp/model/modxmcp.class.php`

Главная серверная логика MODX3 MCP.

Здесь находятся:

- реестр поддерживаемых действий;
- работа с объектами MODX;
- вызов встроенных процессоров MODX;
- работа через xPDO;
- поддержка сторонних дополнений;
- транзакции;
- внутренний журнал действий.

### Интерфейс в менеджере MODX

За страницы компонента в менеджере отвечают:

```text
assets/components/modxmcp/connector.php
assets/components/modxmcp/js/
core/components/modxmcp/controllers/
core/components/modxmcp/processors/mgr/
core/components/modxmcp/templates/
```

Здесь находятся экран настроек и граф зависимостей.

### Встроенная справка для ИИ

```text
core/components/modxmcp/docs/
```

Эти документы доступны агенту через встроенную справку MCP и помогают ему выбирать правильные инструменты.

### Каталог `_build/`

Здесь находятся сборка, установка и проверки проекта.

Основные файлы:

- `build.config.php` — имя и версия транспортного пакета;
- `build.transport.php` — сборка транспортного пакета;
- `install.headless.php` — установка компонента из командной строки без менеджера пакетов;
- `install.transport.php` — установка и удаление транспортного пакета для релизных проверок;
- `release.smoke.sh` — полная проверка релизной сборки;
- `smoke.endpoint.php` — проверка API, установки, повторной установки и удаления;
- `test.release-portability.py` — проверка переносимости и важных правил безопасности;
- `test.client-server-actions.py` — проверка соответствия инструментов клиента серверным действиям;
- `test.modx3-processors.php` — проверка используемых встроенных процессоров MODX 3;
- `data/transport.settings.php` — системные настройки компонента;
- `resolvers/` — действия, выполняемые при установке, обновлении и удалении пакета.

## 4. Что нельзя рассинхронизировать

В проекте есть несколько мест, которые должны всегда соответствовать друг другу.

### Серверные действия

Главный список серверных возможностей находится в:

```php
modxMCP::actionRegistry()
```

Если появляется новая операция, она должна быть зарегистрирована здесь.

### Инструменты, которые видит ИИ

Они описаны в:

```text
client/index.js → toolDefinitions
```

Например, инструмент `modx_example_action` обычно вызывает серверное действие `example_action`.

Автоматический тест проверяет, что список инструментов на стороне Node.js и список действий на стороне PHP не разошлись.

В версии 1.0.0 серверный реестр содержит 182 действия.

### Версия проекта

Номер версии должен совпадать в четырёх местах:

- `_build/build.config.php` → `PKG_VERSION`;
- `package.json` → `version`;
- `package-lock.json`;
- `modxMCP::VERSION`.

Если номера различаются, автоматическая проверка должна завершиться ошибкой.

### Системные настройки

Обычная установка через транспортный пакет и установка из командной строки должны создавать **одинаковый набор системных настроек**.

Сейчас автоматически сравниваются все 16 настроек `modxmcp.*`: значение по умолчанию, тип поля и раздел настроек.

Если добавляется новая настройка, её нужно добавить в оба способа установки.

## 5. Что важно именно для MODX 3

При переходе с MODX 2 на MODX 3 недостаточно заменить несколько имён файлов.

В MODX 3 изменились:

- полные имена PHP-классов;
- пространства имён;
- загрузка ядра;
- расположение встроенных процессоров;
- способ обращения к части процессоров.

Поэтому старый путь процессора из MODX 2 нельзя просто скопировать в MODX3 MCP и считать, что он будет работать.

В проекте есть специальная логика, которая сопоставляет используемое действие с реальным классом процессора MODX 3 и запускает его через `runProcessor()`.

Отдельная проверка убеждается, что все используемые процессоры действительно существуют в поддерживаемых версиях MODX 3:

```bash
php _build/test.modx3-processors.php /path/to/modx/core/src/Revolution/Processors
```

В GitHub эта проверка выполняется для MODX 3.2.2-pl, 3.2.4-pl и актуальной ветки 3.x.

Если вы или ИИ не уверены, какой класс, процессор или поле использовать, правильное действие — **посмотреть актуальный исходный код MODX или нужного дополнения**, а не угадывать.

## 6. Как добавить новую возможность

Даже если вы не программист, этот раздел полезно понимать. По нему можно проверить, что ИИ не добавляет функцию «наугад».

Перед изменением кода нужно ответить на четыре вопроса:

1. Что именно должна сделать новая операция в MODX?
2. Она только читает данные или изменяет сайт?
3. Есть ли уже готовый процессор MODX или установленного дополнения, который умеет это делать?
4. Какая защита нужна перед выполнением: резервная копия, предварительный просмотр, пробный запуск без изменений или явное подтверждение?

### Шаг 1. Добавить действие на сервере

Новое действие добавляется в подходящую группу `actionRegistry()`.

Пример:

```php
'my_action' => 'myAction',
```

Затем реализуется метод `myAction()`.

Не нужно создавать новый способ обработки команд, если существующий реестр уже умеет вызвать нужный метод или процессор.

### Шаг 2. Выбрать правильный способ изменения MODX

Предпочтительный порядок такой.

**1. Использовать встроенный процессор MODX.**

Это лучший вариант, если MODX уже умеет выполнять нужную операцию. Тогда сохраняются стандартные проверки данных, события и обычный жизненный цикл MODX.

**2. Использовать процессор стороннего дополнения.**

Подходит, когда операция относится, например, к miniShop2 или другому компоненту и его процессор можно безопасно вызвать без интерфейса менеджера.

**3. Работать напрямую с объектом xPDO.**

Это запасной вариант. Его следует использовать, когда подходящего процессора нет или он зависит от интерфейса менеджера и не может нормально работать из API.

При прямой работе через xPDO наш код сам отвечает за проверку входных данных и целостность изменения.

Если нужно изучить исходники стороннего дополнения, их копию можно временно положить в каталог `_reference/`. Этот каталог исключён из Git и не попадает в релизный пакет.

### Шаг 3. Добавить инструмент для ИИ

В `client/index.js` нужно добавить описание нового инструмента в список `toolDefinitions`.

Имя обычно имеет вид:

```text
modx_my_action
```

а на сервер передаётся действие:

```text
my_action
```

То есть общий обработчик убирает технический префикс `modx_` и отправляет остальную часть имени на сервер.

Описание инструмента важно: именно по нему ИИ понимает, для чего инструмент предназначен.

В описании желательно явно указать:

- что делает инструмент;
- когда его использовать;
- какие параметры обязательны;
- меняет ли он сайт;
- можно ли сначала посмотреть результат без изменения данных;
- требуется ли явное подтверждение.

### Шаг 4. Указать, является ли операция чтением или изменением

MODX3 MCP различает:

- операции только для чтения;
- операции, которые изменяют сайт.

Это различие влияет на блокировку проекта, резервные копии и журнал изменений.

Новая операция чтения не должна случайно получать ограничения изменяющей операции.

Новая изменяющая операция, наоборот, не должна быть ошибочно помечена как безопасное чтение.

После добавления инструмента нужно проверить соответствующую классификацию в `client/index.js`.

### Шаг 5. Продумать защиту

Для изменяющей операции нужно решить, требуется ли:

- создать резервную копию;
- сначала показать, что будет изменено;
- поддержать пробный запуск без внесения изменений;
- требовать параметр `confirm=true`;
- требовать отдельное разрешение через переменную окружения;
- полностью запретить прямой вызов и разрешать действие только через специальный безопасный порядок.

Защиту нельзя копировать механически с другой операции. Она должна соответствовать реальному риску конкретного действия.

## 7. Правила безопасности, которые нельзя незаметно ослабить

Текущие безопасные значения по умолчанию проверяются автоматически.

Основные правила:

- API требует HTTPS по умолчанию;
- заголовок `X-Forwarded-Proto` не считается доверенным, пока администратор явно не разрешит это для своего прокси-сервера;
- API-токен создаётся с помощью `random_bytes()`;
- токен сравнивается безопасным способом;
- токен нельзя передавать в адресной строке;
- произвольный запуск процессоров MODX выключен по умолчанию;
- чтение произвольных файлов от корня файловой системы выключено по умолчанию;
- автоматическое превращение элементов в статические выключено по умолчанию;
- отладочный режим выключен по умолчанию;
- сервисный пользователь должен быть активным пользователем MODX с правом `sudo`;
- если `service_user_id=0`, компонент сам ищет первого активного пользователя с `sudo`;
- проверка того, разрешена ли группа возможностей, выполняется до запуска самой операции.

Если правка ослабляет хотя бы одно из этих правил, это уже изменение модели безопасности. Его нельзя считать обычной технической чисткой кода.

## 8. Автоматические резервные копии и блокировка одновременных изменений

В Node.js-части есть дополнительная защита для операций, которые меняют сайт.

Для её полноценной работы желательно задать две переменные:

```text
MODX_MCP_SITE_ID
MODX_MCP_MANAGER_ROOT
```

`MODX_MCP_SITE_ID` — понятный идентификатор сайта.

`MODX_MCP_MANAGER_ROOT` — локальный служебный каталог для этого проекта.

В нём создаются:

- `modx-backups/` — автоматические резервные копии перед поддерживаемыми изменениями;
- `project.lock` — файл блокировки, который не даёт двум процессам одновременно менять один и тот же проект.

По умолчанию сохраняется до 20 каталогов автоматических резервных копий.

Количество можно изменить:

```text
MODX_MCP_BACKUP_KEEP_COUNT
```

Переменная:

```text
MODX_MCP_SKIP_AUTO_BACKUP=1
```

отключает автоматические резервные копии на стороне Node.js. На рабочем сайте включать это без понятной причины не рекомендуется.

Если `MODX_MCP_MANAGER_ROOT` не задан, локальная блокировка и часть автоматических резервных копий работать не будут. Серверные проверки и транзакции сохранятся, но общий уровень защиты станет ниже.

## 9. Отдельные разрешения для опасных действий

Некоторые операции специально заблокированы, пока оператор не разрешит их отдельно.

Такие разрешения задаются переменными окружения с именами:

```text
MODX_MCP_ALLOW_...
```

Отдельное разрешение предусмотрено, в частности, для:

- прямого создания некоторых элементов;
- прямого создания плагинов;
- удаления TV, чанков, сниппетов, шаблонов, ресурсов и плагинов;
- массовых изменений ресурсов;
- очистки корзины;
- установки и удаления пакетов;
- изменения поставщиков транспортных пакетов.

Эти разрешения не нужно включать «на всякий случай».

Правильный порядок: сначала понять конкретную задачу и риск, затем временно разрешить только необходимое действие.

## 10. Журнал изменений

В проекте есть два независимых механизма.

### Внутренний журнал компонента

Системная настройка:

```text
modxmcp.audit_log
```

по умолчанию включена.

Сервер записывает сведения о выполненных действиях в собственный журнал компонента.

### Внешний обработчик журнала

Node.js-часть поддерживает переменную:

```text
MODX_MCP_AUDIT_HOOK
```

В неё можно записать путь к локальной программе.

После успешной операции, изменяющей сайт, MODX3 MCP запускает эту программу и передаёт ей через стандартный ввод JSON с данными операции.

Туда входят, в частности:

- название инструмента;
- аргументы;
- результат;
- идентификатор сайта;
- сведения об исполнителе;
- пути к автоматически созданным резервным копиям.

Программа запускается напрямую, без командной оболочки.

Если внешний обработчик не настроен, обычная работа не меняется.

Если он завершился с ошибкой, MODX3 MCP показывает предупреждение, но не сообщает, будто уже выполненное изменение сайта «откатилось» или не произошло.

## 11. Установка из исходного кода

Обычному пользователю лучше устанавливать готовый транспортный пакет из релиза.

Установка непосредственно из исходного кода нужна в основном для разработки, автоматизации и серверов, которыми управляет агент.

Команда:

```bash
php _build/install.headless.php
```

Если `config.core.php` не удаётся найти автоматически:

```bash
MODX_CONFIG_CORE=/full/path/to/config.core.php php _build/install.headless.php
```

Если конфигурация MODX зависит от `DOCUMENT_ROOT`, можно явно указать корневой каталог сайта:

```bash
MODX_DOCUMENT_ROOT=/full/path/to/site \
MODX_CONFIG_CORE=/full/path/to/config.core.php \
php _build/install.headless.php
```

Этот установщик работает только из командной строки и принимает только MODX Revolution 3.x.

Во время установки новые каталоги `core/components/modxmcp` и `assets/components/modxmcp` сначала подготавливаются отдельно.

Рабочие каталоги заменяются только после успешной подготовки.

Если установка не завершилась, предусмотрено восстановление предыдущих файлов.

Изменения пространства имён MODX, пунктов меню, системных настроек и токена выполняются внутри транзакции базы данных, чтобы при ошибке их можно было откатить вместе с установкой файлов.

## 12. Сборка транспортного пакета

Сборщик запускается только из командной строки:

```bash
MODX_CONFIG_CORE=/full/path/to/config.core.php \
php _build/build.transport.php
```

Готовый пакет создаётся в каталоге MODX:

```text
core/packages/
```

Сборщик не должен запускаться через браузер.

Он также откажется собирать пакет с той же подписью версии на установке MODX, где такой пакет уже установлен. Это сделано, чтобы случайно не повредить данные установленного пакета.

## 13. Проверки после изменений

После небольшой правки не нужно сразу выполнять полный цикл установки и удаления. Сначала запускаются подходящие проверки исходного кода.

### Проверка JavaScript

```bash
node --check client/index.js
```

Проверяет синтаксис Node.js-клиента.

### Проверка соответствия клиента и сервера

```bash
python3 _build/test.client-server-actions.py
```

Проверяет, что каждый инструмент, объявленный в Node.js, имеет соответствующее серверное действие и наоборот.

### Проверка переносимости и безопасности

```bash
python3 _build/test.release-portability.py
```

Эта проверка контролирует, среди прочего:

- наличие обязательных файлов;
- одинаковый номер версии во всех нужных местах;
- одинаковый набор системных настроек при установке через транспортный пакет и из командной строки;
- безопасные значения настроек по умолчанию;
- безопасную генерацию API-токена;
- правила выбора сервисного пользователя;
- проверку разрешённых групп возможностей;
- корректную очистку после удаления пакета;
- запрет запуска установщиков через браузер там, где это запрещено;
- правила HTTPS;
- подготовку новых файлов отдельно от рабочих и восстановление при ошибке;
- отсутствие в публичном коде путей и адресов конкретного тестового сервера.

### Проверка PHP

Для каждого изменённого PHP-файла:

```bash
php -l path/to/file.php
```

Перед релизом проверяются все PHP-файлы проекта.

### Проверка встроенных процессоров MODX 3

Если менялась работа со встроенными процессорами MODX:

```bash
php _build/test.modx3-processors.php /path/to/modx/core/src/Revolution/Processors
```

## 14. Автоматические проверки на GitHub

Файл:

```text
.github/workflows/ci.yml
```

описывает автоматические проверки GitHub Actions.

Они проверяют:

- синтаксис PHP;
- синтаксис Node.js;
- синтаксис сценария полной релизной проверки;
- переносимость и основные правила безопасности;
- соответствие клиентских инструментов серверным действиям;
- совпадение версий;
- наличие записи текущей версии в `CHANGELOG.md`;
- совместимость со встроенными процессорами MODX 3.2.2-pl, 3.2.4-pl и текущей ветки 3.x.

Эти проверки полезны, но они не заменяют понимание того, что именно было изменено.

## 15. Полная проверка релизной сборки

Файл:

```text
_build/release.smoke.sh
```

выполняет полный цикл проверки релиза.

Он **меняет состояние установленного компонента**: устанавливает его, выполняет тестовые операции, переустанавливает, удаляет и устанавливает снова.

Поэтому:

> **Никогда не запускайте полный цикл релизной проверки на рабочем сайте. Используйте отдельную тестовую установку MODX 3.**

Запуск:

```bash
MODX_CONFIG_CORE=/full/path/to/config.core.php \
bash _build/release.smoke.sh
```

Сценарий по очереди:

1. проверяет синтаксис PHP;
2. запускает проверки исходного кода;
3. проверяет Node.js-клиент;
4. собирает транспортный пакет;
5. сохраняет текущие настройки тестовой установки;
6. устанавливает пакет;
7. проверяет API и основные операции создания, чтения, изменения и удаления;
8. повторно устанавливает пакет и проверяет, что пользовательские настройки сохранились;
9. полностью удаляет пакет;
10. устанавливает его снова;
11. возвращает исходные настройки;
12. выполняет финальную проверку операций только для чтения.

Для предварительной проверки без цикла установки и удаления:

```bash
bash _build/release.smoke.sh --preflight-only
```

## 16. Обновление версии

Перед новым релизом номер версии нужно изменить согласованно во всех местах, перечисленных выше.

После этого порядок такой:

1. обновить журнал изменений;
2. выполнить проверки исходного кода;
3. выполнить полную релизную проверку на отдельной установке MODX 3;
4. проверить получившийся транспортный пакет;
5. только после этого создавать тег и релиз на GitHub.

Менять версию только в `package.json` нельзя: автоматическая проверка обнаружит расхождение.

## 17. Обслуживание установленной системы

Если вы не разрабатываете код, а только поддерживаете установленный MODX3 MCP, достаточно следить за несколькими вещами.

### Локальная и серверная части должны быть одной версии

Node.js-часть сравнивает свою версию с версией API на сайте и предупреждает, если они различаются.

На рабочем сайте лучше использовать конкретную версию:

```text
github:rumata-estor/modx3-mcp#v1.0.0
```

а не рабочую ветку.

### После обновления сначала проверить чтение

После обновления попросите ИИ:

- показать версию и системную информацию;
- получить несколько известных элементов;
- показать структуру проекта;
- построить граф зависимостей.

Только после этого переходите к изменениям.

### Существующий API-токен должен сохраняться

Оба способа установки специально сохраняют существующие системные настройки и API-токен при повторной установке и обновлении.

### Если сайт работает через обратный прокси-сервер

По умолчанию MODX3 MCP не доверяет заголовку `X-Forwarded-Proto`.

Настройку:

```text
modxmcp.trust_proxy_https
```

следует включать только тогда, когда прокси-сервер находится под вашим контролем и корректно сообщает исходный протокол HTTPS.

## 18. Частые ошибки

### `401 Unauthorized`

Обычно неверно указан `MODX_MCP_TOKEN` или клиент подключён не к тому сайту.

### `HTTPS required`

API считает, что запрос пришёл по HTTP.

Нужно проверить HTTPS и настройки прокси-сервера. Не стоит просто отключать требование HTTPS, чтобы скрыть причину.

### `No active sudo MODX user found`

При `service_user_id=0` компонент не нашёл активного пользователя MODX с правом `sudo`.

Нужно либо создать или активировать подходящего пользователя, либо явно указать корректный `modxmcp.service_user_id`.

### `Capability ... is disabled`

Нужная группа возможностей отключена в настройках MODX3 MCP.

Включайте её только если она действительно нужна для текущей задачи.

### `PROJECT BUSY`

Другой процесс уже выполняет изменяющую операцию и держит блокировку проекта.

Не удаляйте `project.lock` вслепую. Сначала нужно убедиться, что другой процесс действительно завершился.

### Предупреждение о разных версиях

Локальная Node.js-часть и компонент на сайте имеют разные версии.

Нужно привести обе стороны к одной версии.

## 19. Как использовать ИИ, если вы не разработчик

ИИ может помочь разобраться в проекте, подготовить изменение и выполнить большую часть технической работы. Но чем ближе задача к установке на рабочий сайт, правам доступа, пакетам, системным настройкам, API или изменению данных, тем важнее понимать последствия.

Не обязательно читать весь PHP-код самостоятельно. Но перед изменением вы должны получить от ИИ понятное объяснение: что будет затронуто, как будет сделана резервная копия, как проверить результат и как вернуться назад при ошибке.

Если объяснение остаётся непонятным даже после уточнений, это хороший признак того, что задачу лучше сначала выполнить на отдельном тестовом сайте или передать человеку, который уверенно работает с MODX и сервером.

Перед задачей можно дать ему такую инструкцию:

```text
Прочитай DEVELOPMENT.ru.md, README.ru.md и CHANGELOG.ru.md.

Пока ничего не меняй.

Сначала:
1. найди файлы, которые относятся к задаче;
2. объясни простыми русскими словами, как этот участок работает сейчас;
3. перечисли возможные риски;
4. скажи, какие проверки надо выполнить после изменения;
5. только после этого предложи минимальную правку.
```

После изменения:

```text
Проверь сделанную правку по DEVELOPMENT.ru.md.

Запусти подходящие автоматические проверки.
Если менялся PHP — проверь его через php -l.
Если добавлялись или менялись MCP-инструменты — проверь соответствие клиента и сервера.
Если менялись установка, системные настройки или безопасность — запусти проверку переносимости и безопасности.

Покажи простыми словами:
1. что именно проверено;
2. что прошло успешно;
3. что ещё нужно проверить на реальной тестовой установке MODX.
```

Для опасной операции дополнительно спросите:

```text
Какие данные эта операция может повредить?
Создаётся ли резервная копия?
Можно ли сначала увидеть, что будет изменено?
Есть ли пробный запуск без записи данных?
Что произойдёт, если операция оборвётся посередине?
Почему выбран именно этот способ работы с MODX?
Можно ли сначала проверить это на отдельном тестовом сайте?
```

Хороший ответ ИИ должен содержать конкретные механизмы защиты и проверки, а не просто фразу «всё безопасно».

## 20. Что разработчик или ИИ должен объяснить перед серьёзным изменением

Перед значимой правкой должны быть понятны ответы на следующие вопросы:

- какой объект MODX будет изменён;
- каким стандартным механизмом MODX выполняется изменение;
- почему выбран именно этот механизм;
- операция только читает данные или меняет сайт;
- что произойдёт при ошибке;
- нужна ли резервная копия;
- можно ли сначала показать будущие изменения без записи;
- как операция поведёт себя при повторном запуске;
- какие автоматические проверки подтверждают её работу;
- не ослабляются ли настройки безопасности;
- одинаково ли новая функция устанавливается через транспортный пакет и из командной строки.

Если на эти вопросы нет понятного ответа, изменение ещё не готово.

## 21. Что не входит в MODX3 MCP

Telegram-бот, внешние серверные скрипты и внутренний файл `AGENT.md`, которые использовались в нашей рабочей агентной среде, не являются обязательными частями MODX3 MCP.

Проект должен оставаться самостоятельным MCP-сервером и компонентом для MODX.

Его можно подключать к любой совместимой программе или агентной среде с поддержкой MCP.

## 22. Минимальная проверка перед Pull Request или релизом

Базовый набор команд:

```bash
node --check client/index.js
python3 _build/test.client-server-actions.py
python3 _build/test.release-portability.py
bash -n _build/release.smoke.sh
```

Изменённые PHP-файлы дополнительно проверяются через `php -l`.

Если менялась работа со встроенными процессорами MODX 3, выполняется отдельная проверка совместимости процессоров.

Если менялись установка, обновление, удаление, системные настройки, API, изменяющие операции или безопасность, одних проверок исходного кода недостаточно. Нужна отдельная тестовая установка MODX 3 и полный цикл релизной проверки.

> **Рабочий сайт нельзя использовать как стенд для проверки нового установщика, удаления компонента или новой опасной операции.**
