# MODX3 MCP — руководство по разработке и обслуживанию

Этот документ нужен тем, кто хочет **запустить, обслуживать или развивать MODX3 MCP**. Он рассчитан не только на опытных разработчиков. Если вы не знаете внутреннее устройство MODX, Node.js или MCP, этого не требуется знать заранее: ниже объясняется, из каких частей состоит система, где что находится, что можно менять и как проверять результат.

Документ также можно передать ИИ-ассистенту перед работой с проектом. Хороший порядок работы: сначала дать ИИ этот файл, затем поставить конкретную задачу и попросить не менять код, пока он не определит затрагиваемые файлы, риски и проверки.

MODX3 MCP предназначен для **MODX Revolution 3.x**. Старые инструкции для MODX 2 здесь применять нельзя: в MODX 3 изменились пространства имён, классы, загрузка ядра и маршруты процессоров.

> **Главный принцип: не давать агенту максимально широкий доступ. Давать ему правильный, проверяемый и ограниченный доступ к объектам MODX.**

## 1. Как система устроена простыми словами

В MODX3 MCP есть две основные части.

Первая часть устанавливается **на сайт MODX**. Это PHP-компонент, который знает, как работать с ресурсами, шаблонами, чанками, сниппетами, TV, настройками, дополнениями и другими объектами MODX.

Вторая часть запускается **рядом с ИИ-клиентом**. Это Node.js MCP-сервер. Он показывает ИИ набор инструментов вроде «получить чанк», «найти использование элемента», «изменить ресурс» и передаёт выбранную операцию на сайт.

Упрощённая схема:

```text
ИИ / MCP-клиент
      ⇅ stdio
client/index.js
      ⇅ HTTPS + API token
assets/components/modxmcp/api.php
      ⇅
core/components/modxmcp/model/modxmcp.class.php
      ⇅
MODX processors / xPDO / API дополнений
      ⇅
MODX Revolution 3.x
```

То есть ИИ не должен напрямую лезть в таблицы базы данных MODX. Он просит выполнить понятную операцию, а серверная часть выполняет её через структуру MODX.

Отдельно у компонента есть экраны в менеджере MODX, включая настройки и визуальный граф зависимостей.

## 2. Что нужно знать, если вы просто хотите запустить проект

Для обычного использования вам не нужно разбираться во всём исходном коде.

Минимальная схема такая:

1. Установить транспортный пакет MODX3 MCP на сайт.
2. Получить автоматически созданный API-токен.
3. Настроить MCP-клиент так, чтобы он запускал Node.js-часть MODX3 MCP.
4. Передать ей адрес API сайта и токен.
5. Начать с операций только для чтения.
6. Разрешать опасные действия только тогда, когда они действительно нужны.

Готовый транспортный пакет находится в релизах GitHub. Для стабильной версии лучше использовать конкретный тег релиза, а не рабочую ветку.

Пример настройки MCP-клиента:

```json
{
  "mcpServers": {
    "modx": {
      "command": "npx",
      "args": [
        "-y",
        "github:rumata-estor/modx3-mcp#v1.0.0"
      ],
      "env": {
        "MODX_MCP_SITE_URL": "https://example.com/assets/components/modxmcp/api.php",
        "MODX_MCP_TOKEN": "your-token"
      }
    }
  }
}
```

Для локального MCP-сервера нужен **Node.js 18 или новее**.

Если всё подключено правильно, сначала дайте агенту безопасную задачу, например: показать структуру проекта, получить конкретный элемент или построить граф зависимостей.

## 3. Какие части проекта за что отвечают

Если ИИ предлагает изменить файл, полезно понимать, к какой части системы он относится.

```text
client/index.js
```

Локальный MCP-сервер. Здесь описаны инструменты, которые видит ИИ, локальная safety-логика, автоматические резервные копии, project lock и внешний audit hook.

```text
assets/components/modxmcp/api.php
```

HTTP API на сайте. Проверяет HTTPS, токен, размер запроса и передаёт действие серверной модели.

```text
core/components/modxmcp/model/modxmcp.class.php
```

Основная серверная логика. Здесь находится реестр действий, работа с MODX, процессорами, xPDO и дополнениями.

```text
assets/components/modxmcp/connector.php
core/components/modxmcp/controllers/
core/components/modxmcp/processors/mgr/
core/components/modxmcp/templates/
assets/components/modxmcp/js/
```

Интерфейс компонента в менеджере MODX, включая экран настроек и граф зависимостей.

```text
core/components/modxmcp/docs/
```

Встроенная справка для агента. Она доступна через MCP help и помогает модели выбирать правильные инструменты.

```text
_build/
```

Сборка, установка и проверки релиза.

Важные файлы:

- `build.config.php` — версия и имя transport package;
- `build.transport.php` — сборка transport package;
- `install.headless.php` — установка из командной строки без Package Manager;
- `install.transport.php` — установка и удаление transport package в тестах релиза;
- `release.smoke.sh` — полный цикл релизной проверки;
- `smoke.endpoint.php` — проверка API и жизненного цикла;
- `test.release-portability.py` — переносимость и важные security-инварианты;
- `test.client-server-actions.py` — соответствие инструментов клиента серверным действиям;
- `test.modx3-processors.php` — существование используемых процессоров MODX 3;
- `data/transport.settings.php` — системные настройки компонента;
- `resolvers/` — действия при установке, обновлении и удалении.

## 4. Что является источником истины

В проекте есть несколько мест, которые нельзя рассинхронизировать.

### Серверные действия

Главный реестр серверных возможностей находится здесь:

```php
modxMCP::actionRegistry()
```

Если добавляется новая серверная операция, она должна быть зарегистрирована там.

### Инструменты, которые видит ИИ

Они описаны в:

```text
client/index.js → toolDefinitions
```

Инструмент `modx_example_action` обычно соответствует серверному действию `example_action`.

Автоматический тест проверяет соответствие клиента и сервера в обе стороны. В версии 1.0.0 контракт содержит 182 серверных действия.

### Версия проекта

Версия должна совпадать сразу в нескольких местах:

- `_build/build.config.php` → `PKG_VERSION`;
- `package.json` → `version`;
- `package-lock.json`;
- `modxMCP::VERSION`.

CI остановит проверку, если версии различаются.

### Системные настройки

Transport package и headless installer должны создавать одинаковые настройки.

Сейчас автоматически проверяются все 16 настроек `modxmcp.*`: их значение по умолчанию, тип поля и область настроек.

Если добавляете новую настройку, нельзя изменить только один способ установки.

## 5. Как MODX3 MCP работает с MODX 3

MODX 3 использует namespaced PHP-классы и другой способ разрешения core processors, чем старая MODX 2-линия.

Поэтому нельзя просто взять старый путь процессора из примера MODX 2 и предположить, что он работает.

В модели есть helper, который переводит используемые проектом маршруты в реальные классы MODX 3 и запускает их через `runProcessor()`.

Совместимость путей проверяет:

```bash
php _build/test.modx3-processors.php /path/to/modx/core/src/Revolution/Processors
```

В CI эта проверка выполняется против MODX 3.2.2-pl, 3.2.4-pl и актуальной ветки 3.x.

Если вы или ИИ не уверены, какой процессор, класс или поле использовать, **не угадывайте**. Сначала посмотрите актуальный исходный код MODX или нужного дополнения.

## 6. Как добавить новую возможность

Если вы не разработчик, этот раздел всё равно полезен: по нему можно проверить, что ИИ меняет проект правильно.

Перед кодом нужно ответить на четыре вопроса:

1. Что операция делает в терминах MODX?
2. Это чтение или изменение?
3. Можно ли использовать готовый процессор MODX или дополнения?
4. Какие ограничения нужны: backup, dry-run, confirmation или отдельное разрешение?

### Шаг 1. Добавить действие на сервере

Новое действие добавляется в подходящую группу `actionRegistry()`.

Простой пример:

```php
'my_action' => 'myAction',
```

Затем реализуется метод `myAction()`.

Реестр умеет вызывать и методы модели, и процессоры. Не создавайте новый способ dispatch без необходимости.

### Шаг 2. Выбрать правильный способ работы с MODX

Предпочтительный порядок:

**1. Core processor MODX.**  
Используйте его, если MODX уже умеет делать нужную операцию. Так сохраняется встроенная проверка данных и стандартный жизненный цикл MODX.

**2. Processor стороннего дополнения.**  
Используйте его, если действие относится, например, к miniShop2 или другому компоненту и его processor рассчитан на headless-вызов.

**3. xPDO object напрямую.**  
Используйте только когда подходящий processor отсутствует или зависит от Manager UI и не работает headless. В таком случае ответственность за проверку входных данных лежит на нашем коде.

Перед выбором второго или третьего варианта изучите реальные исходники дополнения. Локальные копии для исследования можно держать в `_reference/`; этот каталог исключён из Git и не попадает в пакет.

### Шаг 3. Добавить MCP-инструмент

В `client/index.js` добавляется описание `modx_<action>` в `toolDefinitions`.

Описание инструмента важно не меньше кода: по этому тексту ИИ решает, какой tool использовать.

Хорошее описание должно объяснять:

- что инструмент делает;
- когда его использовать;
- какие параметры обязательны;
- меняет ли он сайт;
- есть ли preview, dry-run или confirmation.

Для большинства операций отдельный JavaScript-handler не нужен. Общий dispatch удаляет префикс `modx_` и отправляет оставшееся имя как серверный action.

### Шаг 4. Правильно отметить чтение и изменение

MODX3 MCP различает read-only и write-операции.

Это влияет на:

- project lock;
- автоматические резервные копии;
- внешний audit hook;
- дополнительные safety-ограничения.

Новая read-only операция не должна случайно считаться изменением. Новая write-операция не должна попасть в список чтения.

После добавления действия проверьте классификацию в `client/index.js`.

### Шаг 5. Добавить защиту для опасной операции

Для изменяющих действий нужно решить, требуется ли:

- backup;
- dry-run;
- `confirm=true`;
- отдельная переменная окружения для opt-in;
- запрет прямого вызова и staged workflow.

Не копируйте safety-логику механически. Ограничение должно соответствовать реальному риску операции.

## 7. Безопасность: что нельзя случайно сломать

Текущие безопасные значения по умолчанию проверяются автоматически.

Основные правила:

- API работает по HTTPS по умолчанию;
- доверие к `X-Forwarded-Proto` выключено, пока администратор не разрешит его явно;
- API-токен генерируется через `random_bytes()`;
- токен сравнивается безопасным способом и не передаётся через query string;
- `run_processor` выключен по умолчанию;
- чтение произвольных файлов от корня файловой системы выключено;
- `auto_static` выключен по умолчанию;
- debug выключен по умолчанию;
- сервисный пользователь должен быть активным пользователем MODX с `sudo`;
- при `service_user_id=0` подходящий активный sudo-пользователь выбирается автоматически;
- capability group проверяется до dispatch операции.

Если изменение ослабляет одно из этих правил, оно должно рассматриваться как изменение модели безопасности, а не как обычный рефакторинг.

## 8. Локальные резервные копии и project lock

В Node.js-клиенте есть дополнительный слой защиты для write-операций.

Для его полноценной работы желательно задать:

```text
MODX_MCP_SITE_ID
MODX_MCP_MANAGER_ROOT
```

`MODX_MCP_MANAGER_ROOT` — локальный каталог, где клиент может хранить служебные данные проекта. В нём создаются:

- `modx-backups/` — автоматические backup перед поддерживаемыми изменениями;
- `project.lock` — блокировка, которая не даёт двум процессам одновременно менять один проект.

По умолчанию хранится до 20 каталогов автоматических backup. Количество можно изменить:

```text
MODX_MCP_BACKUP_KEEP_COUNT
```

`MODX_MCP_SKIP_AUTO_BACKUP=1` отключает этот слой backup. Для обычной работы на живом сайте это не рекомендуется.

Важно: если `MODX_MCP_MANAGER_ROOT` не настроен, локальный project lock и часть автоматических backup клиента не смогут работать. Серверные проверки и транзакции от этого не исчезают, но уровень защиты будет ниже.

## 9. Опасные операции и явные разрешения

Некоторые действия клиент специально блокирует, пока оператор не включит соответствующий opt-in.

В текущей версии отдельные разрешения предусмотрены, в частности, для:

- прямого создания элементов и плагинов;
- staged-удаления TV, чанков, сниппетов, шаблонов, ресурсов и плагинов;
- массовых изменений ресурсов;
- очистки корзины;
- установки и удаления пакетов;
- изменения transport providers.

Переменные имеют имена вида:

```text
MODX_MCP_ALLOW_...
```

Не включайте их «на всякий случай» глобально. Включайте только для конкретного контролируемого workflow и понимайте, какую защиту вы снимаете.

## 10. Аудит

Есть два уровня журнала.

### Внутренний журнал компонента

Настройка:

```text
modxmcp.audit_log
```

по умолчанию включена. Сервер пишет информацию о действиях в журнал компонента.

### Внешний audit hook

Node.js-клиент поддерживает:

```text
MODX_MCP_AUDIT_HOOK
```

После успешной write-операции указанная программа получает JSON через стандартный ввод.

В JSON могут быть:

- название MCP-инструмента;
- аргументы;
- результат;
- идентификатор сайта;
- данные об исполнителе;
- пути к созданным backup.

Программа запускается напрямую, без shell.

Ошибка audit hook не должна превращать уже успешно выполненное изменение сайта в ложную ошибку. Клиент выводит предупреждение и продолжает работу.

## 11. Как установить проект из исходников

Для обычного пользователя предпочтителен готовый transport package из релиза.

Headless-установка нужна для разработки, автоматизации или серверов, которыми управляет агент.

Из корня репозитория:

```bash
php _build/install.headless.php
```

Если `config.core.php` не находится автоматически:

```bash
MODX_CONFIG_CORE=/full/path/to/config.core.php php _build/install.headless.php
```

Если конфигурация MODX зависит от `DOCUMENT_ROOT`, можно явно указать web root:

```bash
MODX_DOCUMENT_ROOT=/full/path/to/site MODX_CONFIG_CORE=/full/path/to/config.core.php php _build/install.headless.php
```

Установщик принимает только MODX Revolution 3.x.

Headless deployment сначала готовит новые `core` и `assets` деревья отдельно, затем меняет рабочие каталоги. При незавершённой установке предусмотрен rollback. Записи namespace, menu, settings и token выполняются в транзакции xPDO.

## 12. Как собрать transport package

Сборщик работает **только из командной строки**.

```bash
MODX_CONFIG_CORE=/full/path/to/config.core.php php _build/build.transport.php
```

Результат создаётся в каталоге MODX:

```text
core/packages/
```

Сборщик не принимает API-токены из URL и не должен запускаться как браузерный installer.

Не собирайте пакет на установке MODX, где уже установлен transport package с той же signature: сборщик специально откажется это делать.

## 13. Проверки во время разработки

После небольшой правки не обязательно сразу запускать полный release smoke.

### JavaScript

```bash
node --check client/index.js
```

### Контракт client/server

```bash
python3 _build/test.client-server-actions.py
```

Тест проверяет, что MCP tools и server actions не разошлись.

### Переносимость и security invariants

```bash
python3 _build/test.release-portability.py
```

Этот тест проверяет, среди прочего:

- обязательные файлы;
- совпадение версий;
- transport/headless settings parity;
- безопасные значения настроек;
- генерацию токена;
- service user;
- capability enforcement;
- uninstall cleanup;
- CLI-only ограничения;
- HTTPS hardening;
- staged deployment и rollback;
- отсутствие привязки к конкретному тестовому серверу.

### PHP lint

Все изменённые PHP-файлы должны проходить:

```bash
php -l path/to/file.php
```

Перед релизом проверяются все PHP-файлы проекта.

### Процессоры MODX 3

Если менялись core processor routes:

```bash
php _build/test.modx3-processors.php /path/to/modx/core/src/Revolution/Processors
```

## 14. CI на GitHub

Workflow находится в:

```text
.github/workflows/ci.yml
```

Он проверяет:

- PHP syntax;
- Node.js syntax;
- shell syntax release runner;
- portability/security test;
- client/server action contract;
- совпадение версий;
- наличие записи текущей версии в CHANGELOG;
- processor compatibility с MODX 3.2.2-pl, 3.2.4-pl и веткой 3.x.

Локальные тесты всё равно нужны. CI — последняя автоматическая проверка, а не замена понимания изменения.

## 15. Полный release smoke

Полный smoke меняет состояние установленного компонента: устанавливает, выполняет CRUD-проверки, переустанавливает, удаляет и снова устанавливает пакет.

**Не запускайте полный release smoke на production-сайте.**

Для полного тестового цикла используйте отдельную MODX 3-установку:

```bash
MODX_CONFIG_CORE=/full/path/to/config.core.php bash _build/release.smoke.sh
```

Сценарий выполняет:

1. PHP lint.
2. Source-regression tests.
3. Проверку Node.js-клиента.
4. Сборку transport package.
5. Снимок существующих настроек.
6. Установку пакета.
7. Endpoint/CRUD smoke.
8. Повторную установку и проверку сохранения настроек.
9. Полное удаление.
10. Финальную установку.
11. Восстановление исходных настроек.
12. Read-only smoke.

Режим:

```bash
bash _build/release.smoke.sh --preflight-only
```

останавливается после предварительных проверок и сборки пакета, не выполняя жизненный цикл install/uninstall.

## 16. Как обновлять версию

Перед новым релизом версия должна быть синхронизирована во всех источниках истины.

После этого:

1. обновите CHANGELOG;
2. выполните локальные проверки;
3. выполните release smoke на отдельном тестовом MODX;
4. проверьте transport package;
5. только после этого создавайте tag/release.

Не меняйте версию только в `package.json`: CI считает это ошибкой.

## 17. Как обслуживать установленный MODX3 MCP

Если вы не разрабатываете код, а только обслуживаете установленную систему, контролируйте несколько вещей.

### Клиент и сервер должны быть одной версии

Node.js-клиент проверяет version endpoint и предупреждает о version skew.

Для production лучше использовать конкретный tag:

```text
github:rumata-estor/modx3-mcp#v1.0.0
```

а не рабочую ветку.

### После обновления начните с read-only проверки

Попросите агента:

- показать версию и информацию о системе;
- получить несколько известных элементов;
- показать структуру проекта;
- построить небольшой dependency graph.

Только после этого переходите к изменяющим операциям.

### Не удаляйте API token при обновлении

Transport и headless installation специально сохраняют существующие значения системных настроек и токен при повторной установке.

### Если сайт стоит за reverse proxy

По умолчанию MODX3 MCP не доверяет `X-Forwarded-Proto`.

Настройку `modxmcp.trust_proxy_https` включайте только если proxy находится под вашим контролем и корректно устанавливает этот заголовок.

## 18. Частые ошибки и что они означают

### 401 Unauthorized

Обычно неверен `MODX_MCP_TOKEN` или клиент подключён не к тому сайту.

### HTTPS required

API видит соединение как HTTP. Проверьте реальный HTTPS и настройки reverse proxy. Не выключайте HTTPS просто для того, чтобы скрыть проблему.

### No active sudo MODX user found

При `service_user_id=0` компонент не нашёл активного MODX-пользователя с `sudo`. Создайте/активируйте подходящего пользователя или явно задайте корректный `modxmcp.service_user_id`.

### Capability ... is disabled

Группа возможностей отключена в настройках MODX3 MCP. Включайте её только если она нужна для текущей задачи.

### PROJECT BUSY

Другой процесс уже держит локальный project lock. Не удаляйте lock вслепую. Сначала убедитесь, что другой процесс действительно завершён.

### Version skew

Версии локального Node.js MCP-сервера и компонента на сайте различаются. Обновите более старую сторону до той же версии.

## 19. Как работать с проектом через ИИ, если вы не программист

Нормальный сценарий — использовать ИИ как разработчика, но не давать ему менять проект без проверки.

Перед задачей можно дать ему такой контекст:

```text
Прочитай DEVELOPMENT.ru.md, README.ru.md и CHANGELOG.ru.md.
Ничего пока не меняй.
Сначала:
1. найди затрагиваемые файлы;
2. объясни простыми словами, как сейчас работает этот участок;
3. перечисли риски;
4. скажи, какие тесты надо выполнить после изменения.
После этого предложи минимальное изменение.
```

После внесения правки попросите ИИ:

```text
Проверь изменение по DEVELOPMENT.ru.md.
Запусти подходящие source tests.
Если менялась PHP-логика — сделай php -l.
Если менялись actions/tools — проверь client/server contract.
Если менялись установка, настройки или безопасность — запусти portability test.
Покажи, что именно было проверено и что осталось проверить на реальном MODX.
```

Для опасного изменения дополнительно спросите:

```text
Какие данные может повредить эта операция?
Есть ли dry-run, backup и rollback?
Почему выбран processor, а не прямое изменение xPDO/БД?
Можно ли проверить это сначала на отдельном тестовом сайте?
```

ИИ не должен отвечать на последний вопрос словами «всё безопасно». Он должен показать конкретный механизм проверки.

## 20. Правило для будущих изменений

Перед объединением любой значимой правки разработчик или ИИ должен уметь ответить:

- какой объект MODX меняется;
- через какой API, processor или xPDO-класс он меняется;
- почему выбран этот способ;
- считается ли действие read или write;
- что произойдёт при ошибке;
- нужна ли резервная копия;
- как операция ведёт себя при повторном запуске;
- какие тесты подтверждают работу;
- не ухудшает ли изменение безопасные значения по умолчанию;
- остаются ли transport и headless installation согласованными.

Если на эти вопросы нет понятного ответа, изменение ещё не готово.

## 21. Что не является частью MODX3 MCP

Telegram-бот, внешние серверные скрипты и внутренний AGENT.md, использованные в нашей рабочей агентной среде, не являются зависимостями проекта.

MODX3 MCP должен оставаться самостоятельным MCP-сервером и MODX-компонентом. Его можно подключать к любой совместимой MCP-среде.

## 22. Перед тем как отправлять Pull Request или выпускать релиз

Минимальная проверка:

```bash
node --check client/index.js
python3 _build/test.client-server-actions.py
python3 _build/test.release-portability.py
bash -n _build/release.smoke.sh
```

Для изменённых PHP-файлов выполните `php -l`.

Если затронуты MODX core processor routes, выполните processor compatibility test.

Если затронуты установка, обновление, удаление, настройки, API, write-операции или безопасность, одной статической проверки недостаточно — используйте отдельную MODX 3-установку и полный release smoke.

Никогда не используйте production-сайт как стенд для проверки installer/uninstaller или нового destructive workflow.
